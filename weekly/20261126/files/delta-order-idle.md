# 订单顾客待机眨眼与小动作

SVN r390 接入了五位棋盘顾客的 Spine。玩家反馈停留时看不到眨眼和随机小动作。乌栗、眠婶和米洛的待机只有循环骨骼曲线。松鼠和警官的眼睑绑定在固定循环，五位顾客都缺少随机待机调度。

素材由原立绘和既有骨架派生。松鼠和警官沿用原眼睑附件，其余角色通过原纹理的局部眼区网格闭合。骨骼无需增加，紧凑裁图按相同眼部形状偏移锚点。运行时由订单半身像实例独立调度，现有棋盘合成和交付通过原接口抢占。

## 待机节奏

- 入场完成后先等 0.65–1.55 秒眨眼。后续眨眼间隔取 2.1–4.4 秒的可见待机时长，眨眼本身约 0.30 秒，有半闭、全闭和睁开。
- 警官的观察和颊羽抖动、松鼠的耳尾动势、乌栗的侧看和甩尾、眠婶的偏头和披巾小动作、米洛的探头和耳朵跟随均由对应的两段 Spine 动作组合。动作之间保留停顿，同一动作最多连续抽到两次。
- 待料和备齐状态有各自的基底姿势。普通重排保留待机倒计时，角色隐去时暂停。成功收单后只暂停该单顾客的待机，并从原接物与感谢入口播放，换单重新排期。

## 复验方式

使用 SVN r390 的隔离客户端叠加本次改动，采用工程固定的 Windows Godot 4.7.2 与专用测试存档。正式入口通过指针从登录进入棋盘，材料齐备由已赚取的检查点构造。验证期间按实际画面查看待机，记录相邻眨眼时点和同屏顾客错峰，随后点击完成交付。

先在原生姿势图中找到乌栗眼睑外露的瞳孔，调整眼眶曲线与网格取样后重新导入。五份加眼睑网格和两份眼睑附件均复看睁眼、闭眼、恢复。生成前后原 PNG 与 atlas 的 SHA-256 相同，两次重建的 Spine 数据一致。

工作区标准包装入口因既有 `client/.agents` 工作副本改动停在来源检查，隔离候选使用该入口选定的同一引擎实跑。CodeGraphContext 查询遇本机启动路径错误，实际调用沿棋盘角色绑定、订单接受和角色回收源码复核。Android 真机及性能预算留待目标包复验。

## 本轮结果

- 七套绑定的原生姿势和生命周期检查共 215 项通过。确认闭眼可见、睁眼像素还原、交付抢占待机、换单与重排保留正确的订单状态。
- 正式棋盘入口复跑 13 组共 689 项，覆盖 432×720、432×936、432×1000。五位顾客均在长屏实际完成等待、眨眼、小动作和交付。双单录制中两位顾客首次眨眼相差 421 毫秒，第二次相差约 2.4 秒。交付、拒绝保存后重试、改窗、奖励飞行时退出再进均通过。
- 合成复验中一条旧断言误把备齐待机中的眨眼视为错误。调整为同时验证备齐基底和允许的待机动作，长短屏重跑各 55 项通过。原失败单独保留。
- 原始结果位于 `LocalOnly/order-idle-20261125/poses-final/pose-result.json` 及同目录下各场景的 `proof/pointer-result.json`。连续录制存为 `order-guests-idle-432x936.gif`。未生成 Android 包。
